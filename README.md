# Apps Promo

Shared "Our other apps" catalog and WinUI 3 page for the apps from Dynamic Solutions (CA). Each Windows app bundles this as a git submodule; the page cross-promotes the publisher's Store and web apps and automatically hides the app it is running inside (matched by package family name).

App data (names, blurbs, destinations, icons) is generated by `refresh-catalog.ps1` and committed as static assets. Consuming apps fetch the public manifest when the promo page opens, then persist the last successful manifest and icons in app-local storage. Bundled assets remain an offline first-run fallback, so the page renders even when GitHub is unavailable.

The public generated manifest is also available at `https://raw.githubusercontent.com/Dynamic-Solutions-Canada/apps-promo/main/Assets/PromotedApps/apps.json`.

## Consuming (per app, one-time)

```powershell
git submodule add https://github.com/Dynamic-Solutions-Canada/apps-promo external/promo
```

In the app's `.csproj`:

```xml
<Import Project="external\promo\PromotedApps.projitems" Label="Shared" />
```

Add a nav item (e.g. in `NavigationView.FooterMenuItems`) that navigates to `TechnicallyReal.Promo.PromotedAppsPage`.

CI note: checkouts need submodules, e.g. `actions/checkout` with `submodules: true`.

## Host requirements

From v2.0.0 the page uses the family page standard (UI-3) and takes its styles from the host app; it carries no copy of them. Merge winui-app-kit's shared styles, from kit tag v1.2.0 or later, in the app's `App.xaml` after `XamlControlsResources` (see "Shared XAML" in the kit README):

```xml
<ResourceDictionary Source="ms-appx:///WinUIAppKit/Styles.xaml" />
```

The page uses these keys from it:

| Key                | Use on the page                                    |
| ------------------ | -------------------------------------------------- |
| `PageContentStyle` | The page's content: padding, spacing and max width |
| `PageTitleStyle`   | "Our other apps"                                   |
| `CardBorderStyle`  | Each app's card                                    |

It also uses `CaptionTextBlockStyle` and `TextFillColorSecondaryBrush`, which every WinUI app has through `XamlControlsResources`. An app that defines these keys itself works too, but WinUI looks them up only when the page opens: a host without them builds, then fails to open the page. Stay on promo v1.x until the app merges the kit styles.

## Narrow widths

From v2.1.0 each card adapts to its own width. The icon, the app's name and description, and the button sit in a row while the text keeps at least 240 epx; below that, the button moves under the text. The switch depends on the card, not the window, because the space a card gets also depends on the host's navigation pane and on how long the button's label is in the current language. With the kit's padding and an English label, a card stacks below roughly 450 epx, which is a page narrower than about 520 epx. The layout is `TrailingActionPanel` in `Views/`, and the 240 is `MinContentWidth` in the page XAML.

## Page language (optional)

The WinUI page bundles its own UI text (title, subtitle, and the known action labels "View in Store", "Visit website", "Open") in `Views/PromoLocalization.cs`, in the same nine locale identities the apps use: `en-US`, `en-CA`, `es-ES`, `fr-FR`, `fr-CA`, `de-DE`, `zh-CN`, `pt-BR`, `ja-JP`. Canadian locales reuse the en-US / fr-FR wording; anything unsupported (including Traditional Chinese) falls back to English. From v2.2.0 each app's description comes from the manifest in the same language (see "Translated descriptions"); app names are never translated.

Apps that do nothing get Windows' preferred languages. Apps with their own language setting point the page at it once at startup and refresh it when the language changes:

```csharp
TechnicallyReal.Promo.PromoLocalization.LocaleProvider = () => UiText.Locale; // e.g. "fr-CA"; null = follow Windows
UiText.Changed += TechnicallyReal.Promo.PromoLocalization.Refresh;             // open promo pages re-apply their text
```

The page never references a consumer's localization classes. When adding a string, key it by the English text and add it to every table in `PromoLocalization.cs`.

## Web and Android consumers

`catalog.ts` exports the public manifest URL, types, and `parseCatalog` validation. Each entry has a stable `appId` for hiding the current product across platforms, and `links` containing a platform (`Android`, `Windows`, or `Web`), HTTPS URL, and action label. Use HTTPS Microsoft Store listings on Android, rather than the Windows-only `ms-windows-store:` scheme. Keep the original `destination`, `actionLabel`, and `packageFamilyName` fields for shipped WinUI consumers.

Show each description with `blurbFor(app, locale)`, which takes the app's BCP-47 locale tag (`fr-CA`, for example), picks the translation the WinUI page would, and falls back to the English `blurb`. An app that translates blurbs itself, for example through `promo.*` message keys, can drop those keys.

Import the bundled JSON and icons for the first offline visit. Refresh the public manifest when the page opens, without credentials, validate before storing it, and retain the last successful catalog if the network or validation fails. Cache new remote icons for offline use. Show platform labels on every app and hide the consuming product by `appId`, rather than comparing display names.

The consumer's checkout and build context must include this submodule. Catalog metadata edits go in `ids.json` as well as the generated manifest so a later `refresh-catalog.ps1` run preserves them.

`appOrder` in `ids.json` sets the shared display order across Store and web apps. Every app must appear exactly once. Consumers retain that order when hiding their own product. An optional `name` in `appOverrides` pins a publisher-approved display name instead of the current Store listing title; stable `appId` values remain unchanged when a product is renamed.

Little Launcher's catalog description covers Windows and Linux AppImage. Keep that wording in `ids.json` under `blurbOverrides` as well as the generated manifest so refreshes preserve it. Its existing Store destination is for Windows; Linux AppImage downloads are available from the Little Launcher GitHub releases page.

## Updating the promoted apps

1. Add/remove Store product IDs in `ids.json` and add their stable `appId` and platform `links` under `appOverrides` (optionally set a `blurbOverrides` entry to replace the auto-extracted first line of the Store description). Add web apps, and apps with no Microsoft Store listing, under `externalApps`, including a destination and a repository-owned icon URL. Give a Store product an `iconUrl` in its `appOverrides` entry once its 256 px icon exists (see "Icons").
2. Run `npm run catalog:refresh` (or `.\scripts\refresh-catalog.ps1`) in Windows PowerShell: it queries the Store's StoreEdgeFD endpoint and regenerates `Assets/PromotedApps/apps.json` plus the icon files.
3. Translate any new or changed English blurb (see "Translated descriptions"): add the app's `blurbTranslations` entry in `ids.json`, and the same six texts as its `blurbs` in the manifest. The refresh warns about an app with missing translations and writes the ones it has. A new Store product's English is known only after the refresh, so translate it then.
4. Run `npm run validate`, which checks that `ids.json`, the manifest, the translations and the icons still agree. Then review, commit, and push the diff. Existing app releases receive the update the next time their promo page opens, so a catalog-only change needs no release and no pin bump (see "Versioning").

`refresh-catalog.ps1` is the only thing that talks to the Store backend. The runtime only reads the committed GitHub manifest and its icons, so Store endpoint changes cannot break shipped apps.

## Translated descriptions

Every app's description is translated into the page's other six wording catalogs: `es-ES`, `fr-FR`, `de-DE`, `zh-CN`, `pt-BR` and `ja-JP`. `en-CA` reads the English and `fr-CA` reads `fr-FR`. The English stays in `blurb`, and the translations sit beside it in each app's `blurbs` in the manifest. They are written in `ids.json` under `blurbTranslations`, keyed by `appId`, and the refresh copies them across.

Each `blurbTranslations` entry records, as `source`, the English it was translated from. `npm run check:catalog` fails when an app is missing a translation, when `ids.json` and the manifest disagree, or when an app's English no longer matches its `source`. So after changing an app's English (a `blurbOverrides` entry, an `externalApps` blurb, or a refreshed Store description), translate it again into all six and set `source` to the new English.

## Icons

Catalog icons are 256 px squares, taken from each app repo at `assets/generated/icon-256.png` through the entry's `iconUrl` (in `appOverrides` for a Store product, in `externalApps` otherwise). Until an app repo publishes that file, its entry keeps its current icon: the Store's 50 px logo for Store products, and PrintStream's 192 px web icon.

- `npm run catalog:refresh` uses an entry's `iconUrl` in place of the Store logo, refuses an icon that is not a square PNG, and warns while an icon is not 256 px.
- `npm run check:catalog` fails when an icon is missing, is not a square PNG, or comes from `assets/generated/icon-256.png` without being 256 px. It lists the entries still below 256 px without failing.
- Point an entry at an app repo's icon only once the file is published there; the refresh downloads it.

| PhoneLock            | A Google Play listing                                  | `externalApps` entry with the Play link as destination and Android link                      |
| SonarBridge          | A Google Play listing                                  | `externalApps` entry with the Play link as destination and Android link                      |

Every new entry also needs its app repo's 256 px icon at `assets/generated/icon-256.png` for its `iconUrl`, a place in `appOrder`, and its description in all six translated wording catalogs under `blurbTranslations`. Internal and client-specific apps are not listed.

## Versioning

Each release is an annotated `vX.Y.Z` tag with a GitHub Release whose notes say what changed for apps. The version lives in `package.json`, and the notes for each version are committed in `release-notes/`. Versions follow SemVer:

- **Major:** anything that needs an edit in a consuming app: renaming or removing anything listed under "Permanent URLs" or in the "Consuming" steps, a new resource the host app must provide, or a change to the `catalog.ts` contract that breaks existing callers.
- **Minor:** new page or `catalog.ts` behaviour that needs no edit in the app.
- **Patch:** fixes that do not change documented behaviour.

Apps pin a tag, never a bare commit, and every app stays on the same tag. When the page's code changes (layout, localization, fetch logic), each app bumps its pin in its next release at the latest. A catalog-only change (`ids.json` and `Assets/PromotedApps/`) is not released and needs no bump, because the catalog reaches shipped apps at runtime. To take a new version, check the tag out in the submodule and commit the pin bump with the subject `Update Apps Promo: <what it changes for this app>`:

```bash
git -C external/promo fetch --tags
git -C external/promo checkout vX.Y.Z
```

### Moving from an old pin

An app pinned to a bare commit, or to a version before v2.0.0, makes these changes when it moves to the current tag. Each Release's notes cover the same steps one version at a time.

1. Merge winui-app-kit's shared styles, from kit v1.2.0 or later, as "Host requirements" shows. Without them the page fails when it opens.
2. Delete the app's `PromotedAppsPage.Localization.cs` translation adapter, if it has one. The page translates itself; see "Page language".
3. If a build check outside the app compiles the page's code-behind against stubs of its XAML, it needs stubs for `AppList`, `TitleText` and `SubtitleText`.
4. Point anything that matches catalog URLs, such as a web service worker's cache rule for icons, at `https://raw.githubusercontent.com/Dynamic-Solutions-Canada/apps-promo/main/Assets/PromotedApps/`, the base `CATALOG_BASE_URL` uses. Rules written for the old `RyanEwen/technicallyreal-promo` path no longer match, so icons are not cached for offline use.
5. Replace any copy of the page's subtitle the app keeps for its own promo pages (web, Linux, shared message catalogs) with "More apps from Dynamic Solutions (CA).", and update its translations.

## Permanent URLs

Installed copies of every shipped app fetch the catalog from a fixed URL, and they cannot be patched. App releases before this repo's rename fetch it through the old name, `RyanEwen/technicallyreal-promo`, which GitHub redirects here. That redirect holds only while the old name stays unused, so never create a repository at `RyanEwen/technicallyreal-promo`. For the same reason, `Assets/PromotedApps/apps.json` on `main` must never be renamed or moved.
